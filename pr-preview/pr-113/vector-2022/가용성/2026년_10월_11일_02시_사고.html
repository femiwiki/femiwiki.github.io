10월 11일 2시 47분부터 2시 59분까지 12분 동안 캐시에 없는 페미위키 문서는 10초가 지나서야 열렸고, 편집 저장이나 로그인처럼 내용을 보내는 요청은 503 오류를 받았습니다. 10초를 기다리지 못하고 끊긴 요청까지 더해 웹 서버 응답의 24%가 503이었습니다. 새 이미지가 웹 서버의 PHP 상태 확인이 찾던 파일을 지웠기 때문이고, 이미지를 이전 것으로 되돌려 고쳤습니다. 배포 전 확인은 모두 이 상태 확인을 거치지 않아 배포는 성공으로 끝났습니다. 그 뒤 상태 확인이 웹 루트를 묻도록 웹 서버 설정을 고치고 새 이미지를 다시 내보냈습니다.

원인

docker-mediawiki#1479는 웹 루트를 미디어위키 전체에서 /srv/docroot로 줄이는 작업의 4단계로,[3] 옛 웹 루트 /srv/femiwiki.com에 한 세대 동안 남겨 두었던 링크 다섯 개를 지웠습니다.[4] 그 가운데 healthz.php가 있었습니다.

웹 서버 Caddy는 PHP 컨테이너의 포트에 1초마다 /healthz.php를 물어 건강한 포트로만 요청을 보냅니다.[5] 이 상태 확인은 사이트의 웹 루트가 아니라 Caddy가 실행된 디렉터리를 기준으로 파일 경로를 만드는데,[6] Caddy는 /srv/femiwiki.com에서 실행됩니다.[7] 그래서 상태 확인은 웹 루트를 옮긴 3단계 뒤에도 링크로만 남은 /srv/femiwiki.com/healthz.php를 물었고, 링크가 사라진 98번째 세대에서는 PHP 컨테이너가 멀쩡한데도 건강한 포트가 하나도 없다고 판정했습니다.

건강한 포트가 없으면 Caddy는 10초 동안 기다린 뒤 503을 냅니다.[8] 이 503은 대체 경로가 받아서, GET과 HEAD 요청은 상태 확인 없이 PHP로 다시 보내고 나머지에는 503을 그대로 돌려줍니다.[9] 그래서 캐시에 없는 읽기는 모두 10초 늦게 답을 받았고, 편집 저장이나 로그인 같은 POST 요청은 실패했습니다.

2시 47분 16초부터 2시 59분 36초까지 http-98이 받은 요청 1,645건 가운데 1,009건(61%)이 10초를 기다려 대체 경로로 갔습니다. 그 가운데 633건은 답을 받았고(200이 567건), 376건은 503으로 남았습니다. 376건 가운데 363건은 대체 경로가 PHP에 연결하려 할 때 요청이 이미 취소되어 있었습니다. 10초를 기다리지 않고 끊긴 요청으로, Route 53 상태 확인 132건이 모두 이렇게 끝났습니다. 대체 경로를 거치지 않은 503은 POST 23건이어서 503은 모두 399건(24%)입니다. 대체 경로를 거치지 않은 200 593건은 PHP를 거치지 않은 캐시된 응답과 정적 파일입니다. Route 53 상태 확인 283건을 빼면 1,362건 가운데 877건(64%)이 10초를 기다렸고 267건(20%)이 503이었습니다. 되돌린 뒤 http-99는 3시 5분까지 708건에 답했고 5xx는 없었습니다. 수치는 모두 Grafana Cloud Loki에 남은 웹 서버 접근 로그와 오류 로그(http-97, http-98, http-99)에서 센 것입니다.

왜 배포가 통과했나

배포는 새 컨테이너가 건강하다고 답한 뒤 옛 세대를 지웁니다. 그 사이의 확인 가운데 Caddy의 상태 확인과 같은 경로를 묻는 것은 없었습니다.[10]

  • 배포 계획 단계의 설정 확인(infra#1282)은 1시 사고 뒤에 더한 것으로, 새 PHP 이미지가 설정을 읽는지만 봅니다.[11] 웹 서버를 거치지 않으므로 이번에도 통과했습니다.
  • PHP 컨테이너의 예열 확인(docker-mediawiki#1477)도 1시 사고 뒤에 더한 것으로, PHP에 직접 문서 세 개를 요청해 5xx가 나오면 컨테이너가 요청을 받지 않게 합니다.[12] docker-mediawiki#1479는 예열이 묻는 경로도 /srv/docroot로 바꾸었으므로[13] 예열은 세 문서 모두 200을 받았습니다.
  • PHP 컨테이너의 건강 검사는 웹 루트 밖의 검사 스크립트를, 웹 서버의 건강 검사는 Caddy가 PHP 없이 답하는 주소를 묻습니다.[14][15]

1시 사고 뒤에 더한 확인은 PHP가 설정을 읽지 못하는 경우를 막는 것이라, PHP는 멀쩡하고 웹 서버가 PHP를 찾지 못하는 이번 경우는 다루지 않았습니다.

알림

울린 것은 Route 53 경보 하나였고, Grafana 경보는 이 사고 동안 하나도 상태가 바뀌지 않았습니다.[10] 까닭은 둘입니다.

첫째, 서버 오류 경보는 대체 경로의 응답을 세지 않았습니다. 대체 경로는 원래 배포 중의 짧은 틈을 메우려고 둔 것이라, 대체 경로가 돌려준 정상 응답이 사이트 다운 경보를 속이지 않게 표시를 달아 두었는데, 서버 오류를 세는 쪽도 같은 표시로 대체 경로의 503을 뺐습니다. 이번 503 399건 가운데 376건이 대체 경로에서 나왔으므로, 경보가 본 503은 POST 23건뿐이었습니다. 사이트 다운 경보는 캐시된 정상 응답이 계속 나가 울릴 까닭이 없었습니다.

둘째, 2분 동안 요청의 30%가 넘게 실패하면 울리게 infra#1286에서 더한 경보가 사고 16분 전에 지워져 있었습니다. 그 뒤에 승인된 다른 변경(infra#1289)이 #1286보다 오래된 코드로 Grafana를 다시 적용하면서 이 규칙을 되돌렸기 때문입니다.[16] 규칙이 남아 있었더라도 첫째와 같은 까닭으로 울리지 않았을 것입니다.

Route 53의 특수:빈문서 확인 경보가 2시 54분 1초에 울렸고 3시 3분 1초에 풀렸습니다. 페미위키:대문 확인은 웹 서버 캐시가 대문을 내주어 끝까지 정상이었습니다.

고친 것

  • 이미지를 97번째 세대가 쓰던 2026-10-10T17-04-5e8a1bf8로 되돌려 99번째 세대로 배포했습니다.[2] infra#1294가 저장소를 그에 맞추었습니다. 첫 시도는 세대 번호를 커밋에 넣지 않아 세대 번호 확인에서 멈췄고, 이 때문에 복구가 2분쯤 늦어졌습니다.
  • 되돌리기 절차에 세대 번호를 커밋하는 단계를 넣었습니다. infra#1295에서 고쳐 3시 4분 54초에 반영했습니다.
  • 서버 오류 경보와 2분 경보가 대체 경로의 503도 세게 하고, 지워진 2분 경보를 되살렸습니다. infra#1297에서 고쳐 3시 11분에 적용했습니다. 접근 로그로 다시 세면 이번 사고에서 서버 오류 경보는 2시 57분쯤 울렸을 것입니다.
  • Caddy의 상태 확인이 실행 디렉터리가 아니라 웹 루트 /srv/docroot를 기준으로 경로를 만들게 했습니다. infra#1296에서 고쳐 3시 21분 39초에 100번째 세대로 적용했고, 그 뒤 9분 동안 http-100이 받은 1,606건 가운데 5xx와 대체 경로 응답은 없었습니다.
  • docker-mediawiki#1479를 담은 이미지 2026-10-10T18-27-a531a71f를 다시 내보냈습니다. infra#1299로 3시 38분 32초에 101번째 세대로 적용했고, 그 뒤 9분 동안 http-101이 받은 957건 가운데 5xx와 대체 경로 응답은 없었으며 예열도 /srv/docroot를 거쳐 세 문서 모두 200을 받았습니다. 웹 루트를 줄이는 작업은 docker-mediawiki#1333에서 마쳤습니다.

남은 문제

  • 배포 전 확인은 새 세대를 웹 서버를 거쳐 열어 보지 않습니다. infra#1104에서 다룹니다.
  • main보다 오래된 코드로 계획한 적용이 그 사이 main이 적용한 것을 되돌릴 수 있습니다. 적용 직전에 이를 막는 확인을 infra#1298에서 다룹니다.
