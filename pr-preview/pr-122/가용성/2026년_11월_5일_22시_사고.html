        11월 5일 22시 28분 21초부터 1분 동안 캐시에 없는 페미위키 문서가 늦게 열렸습니다. 웹 서버가 이 동안 끝낸 요청 168건 가운데 63건이 5초에서 27초 걸렸고, 3건은 10초 넘게 기다리다 이용자 쪽에서 끊었습니다. 오류 응답은 없었습니다. 같은 때 새 이미지의 배포가 실패했는데, 새 웹 서버가 아직 데워지지 않은 새 PHP 컨테이너에 확인 요청을 보냈다가 시간을 넘긴 탓입니다. 이전 웹 서버가 계속 요청을 받아 배포 실패 자체는 이용자에게 드러나지 않았고, 새 웹 서버가 새 PHP 컨테이너가 준비된 뒤에 뜨도록 순서를 고쳐 다시 배포했습니다.

        원인

        웹 서버의 시작 스크립트는 공개 포트를 열기 전에 대문, 검색, load.php 같은 주소를 직접 요청해 보고, 하나라도 30초 안에 바른 답을 받지 못하면 끝납니다.[3][4] 배포는 새 웹 서버와 새 PHP 컨테이너를 서로 기다리지 않고 함께 띄웠기 때문에, 이 확인은 아직 예열 중인 fastcgi-177에 닿았습니다. fastcgi-177은 새 이미지에서 처음 뜬 PHP 컨테이너여서 load.php?modules=startup을 처음부터 만들어야 했고, 이 요청이 30초를 넘겼습니다.

        Docker가 웹 서버를 다시 시작하자 두 번째 확인은 통과했고 22초 만에 요청을 받기 시작했습니다. 그러나 배포는 새 웹 서버가 건강해지기를 60초까지만 기다렸고,[5] 다시 시작한 웹 서버는 그보다 13초 늦게 건강해졌습니다. 배포는 실패로 멈췄고 OpenTofu 상태에는 http-177이 오염된(tainted) 것으로, http-176은 아직 지우지 못한 것으로 남았습니다. 이전 PHP 컨테이너는 웹 서버와 순서가 묶여 있지 않아 이미 지워진 뒤였고, http-176은 두 포트를 모두 보는 설정이라 fastcgi-177을 통해 계속 답했습니다.

        이용자가 겪은 것

        22시 28분 19초부터 1분 동안 http-176이 끝낸 요청은 168건이고, 그 가운데 63건이 5초 넘게 걸렸습니다. 가장 오래 걸린 것은 27.7초였습니다. 끊긴 3건은 각각 10.1초, 10.6초, 11.4초를 기다렸습니다. 같은 날 178번째 세대를 배포할 때는 5초 넘게 걸린 요청이 1분에 2건 이하였습니다. 22시 28분부터 22시 58분까지 이용자에게 나간 5xx는 없었습니다.

        http-176이 18건의 502를 냈지만 모두 서버 지표를 모으는 Alloy가 지워진 fastcgi-176의 상태 페이지를 물은 것으로, 이용자의 요청이 아니었습니다.

        이 1분 동안 이전 PHP 컨테이너의 응답이 왜 늦었는지는 알지 못합니다. 새 PHP 컨테이너의 예열, 웹 서버의 확인, 잡 러너 교체가 한꺼번에 서버를 바쁘게 한 것으로 보이지만, 서버의 메모리 지표가 22시 28분부터 1분 반 동안 비어 있어 확인하지 못했습니다.

        요청 수와 응답 시간은 Grafana Cloud Loki의 웹 서버 접근 로그(http-176, http-177, http-178), 502는 Caddy 지표, 시작 과정은 http-177의 로그에서 센 것입니다.

        알림

        배포 실패는 Discord에 알림이 갔습니다. 독자 영향 경보는 하나도 울리지 않았습니다.

        고친 것

        • http-176을 손으로 내린 뒤 같은 이미지를 178번째 세대로 다시 배포했습니다. 오염된 http-177은 이름이 같은 컨테이너로 바꿀 수 없어 세대 번호를 하나 올렸습니다.
        • 새 웹 서버가 새 PHP 컨테이너가 건강해진 뒤에 뜨고, 이전 PHP 컨테이너는 이전 웹 서버가 내려간 뒤에 지워지게 했습니다. infra#1597에서 고쳐 22시 48분에 적용했고, 이 배포에서 웹 서버의 확인은 첫 시도에 통과했습니다.
        • PHP 컨테이너의 예열에 load.php?modules=startup을 더했습니다. docker-mediawiki#1767에서 고쳤고 다음 이미지 배포에 들어갑니다.
        • PHP 컨테이너의 예열과 웹 서버의 확인이 같은 주소 목록을 읽게 했습니다. 확인하는 주소를 늘릴 때 예열에서 빠뜨리는 일이 다시 생기지 않습니다. docker-mediawiki#1770
        • 새 웹 서버가 뜨지 못했을 때의 복구 절차를 적었습니다. infra#1598
