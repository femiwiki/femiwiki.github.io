      10월 11일 1시 20분부터 1시 27분까지 7분 가까이 페미위키에 들어온 요청의 72%가 빈 500 오류를 받았습니다. 캐시에 없는 문서는 열리지 않았고 편집도 할 수 없었습니다. 새 이미지에서 사라진 상수를 운영 설정이 여전히 쓰고 있어 PHP가 모든 요청에서 멈췄고, 그 두 줄을 지운 설정을 다시 배포해 고쳤습니다. 배포 전 확인이 모두 설정을 읽지 않는 검사여서 배포는 성공으로 끝났고, 이를 막는 일은 아직 남아 있습니다.

      원인

      docker-mediawiki#1466은 이미지의 LocalSettings.php에서 NS_GADGET로 시작하는 이름공간 상수 네 개를 지웠습니다.[3] 가젯 저장 방식을 바꿔 그 이름공간들이 더는 없기 때문입니다. 이미지 안에서는 이 상수를 쓰는 곳이 없었습니다.

      그러나 운영 설정 저장소에 있는 핫픽스 파일은 문서 모델을 지정하는 목록에서 그 가운데 NS_GADGET_TALK와 NS_GADGET_DEFINITION_TALK를 여전히 썼습니다.[4] 이 파일은 배포할 때 환경 변수로 컨테이너에 넣어지고,[5] LocalSettings.php가 요청마다 읽습니다.[6] 그래서 새 이미지에서는 PHP가 모든 요청에서 Undefined constant "NS_GADGET_TALK" 오류로 멈추고 본문 없는 500을 돌려주었습니다. 이미지에 든 핫픽스 파일은 개발용이라 이 상수를 쓰지 않았고, 운영 핫픽스 파일은 배포할 때에야 새 이미지와 만납니다.

      배포는 새 PHP 컨테이너가 건강하다고 답할 때까지 기다린 뒤 옛 세대를 지우는데, 그 건강 검사와 웹 서버의 상태 확인은 모두 설정 파일을 읽지 않습니다. 설정을 읽어 실제 문서를 그리는 것은 컨테이너가 뜰 때 문서 세 개를 미리 여는 예열 단계뿐이었고, 예열은 1시 20분 54초부터 9초 동안 18번 모두 500을 받았지만 결과와 상관없이 끝난 것으로 처리되었습니다.[7] 그래서 새 세대가 건강하다고 보고되었고 92번째 세대는 지워졌습니다. 되돌릴 옛 세대가 없었으므로 복구는 고친 설정으로 새 세대를 하나 더 배포하는 수밖에 없었습니다.

      1시 20분 55초부터 1시 27분 40초까지 웹 서버가 받은 요청 501건 가운데 363건(72%)이 500이었습니다. Route 53 상태 확인 161건을 빼면 340건 가운데 285건(84%)입니다. PHP 컨테이너(fastcgi-93)에는 같은 치명적 오류가 382건 남았습니다. 상태 확인을 뺀 정상 응답 55건 가운데 17건은 처리하던 요청을 마저 끝내던 옛 웹 서버(http-92)가 돌려준 것이고, 나머지는 PHP를 거치지 않은 캐시된 응답과 정적 파일입니다. 94번째 세대의 웹 서버도 새 PHP 컨테이너가 뜨기 전 12초 동안 옛 PHP 컨테이너로 보낸 9건에서 500을 받았습니다. 수치는 모두 Grafana Cloud Loki에 남은 웹 서버 접근 로그(http-92, http-93, http-94)와 PHP 로그(fastcgi-93, fastcgi-94)에서 센 것입니다.

      알림

      경보는 모두 7분 넘게 오류가 이어져야 울리게 되어 있어, 사고가 끝난 뒤에 울리거나 끝내 울리지 않았습니다.[7] 서버 오류 경보는 1시 23분에 대기 상태가 되어 1시 28분 30초에 울렸습니다. 사이트 다운 경보는 5분 동안의 정상 응답 수를 보는데, 그 창에 사고 전의 정상 응답과 캐시된 응답이 남아 있어 1시 25분에 대기 상태가 되었다가 울리지 않고 풀렸습니다. Route 53의 특수:빈문서 확인은 1시 23분부터 실패했지만 경보는 5분 연속 실패를 기다려 1시 28분 1초에 울렸고, 페미위키:대문 확인은 웹 서버 캐시가 대문을 내주어 끝까지 정상이었습니다. 사고는 경보가 아니라 배포 뒤 점검에서 발견되었습니다.

      고친 것

      • 운영 핫픽스 파일에서 두 상수를 지웠습니다. infra#1280에서 고쳐 94번째 세대로 배포했고, 1시 27분 39초 뒤로 500과 치명적 오류가 나가지 않은 것을 확인했습니다.

      남은 문제

      • 설정을 읽지 못하는 세대도 배포 전 확인을 모두 통과하고, 되돌리는 절차도 없습니다. 예열이 실패하면 새 세대가 요청을 받지 않게 하는 것, 배포 계획 단계에서 새 이미지가 설정을 읽는지 확인하는 것, 되돌리는 절차를 적는 것을 infra#1281에서 다룹니다.
      • 경보가 사고보다 늦습니다. 2분 동안 요청의 30%가 넘게 실패하면 울리는 경보를 infra#1286에서 더하고 있고, 이번 사고였다면 1시 25분 30초쯤 울렸을 것입니다.
